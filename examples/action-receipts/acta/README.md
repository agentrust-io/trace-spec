# Acta decision receipts as action-receipt evidence

These fixtures are a second action-receipt profile alongside the embodied one
in the parent directory. Where that profile evidences a physical action taken
by an external controller (a robot arm, a safety monitor), this one evidences
a **software decision**: an AI agent's tool call, evaluated and decided by a
local policy gate before it runs. Same verification pattern from
[spec section 3.3.2](../../../spec/trace-v0.1.md#332-action-receipts-for-embodied-workflows-informative),
different action class, and the two should not be conflated: nothing here
claims a physical outcome.

Full field mapping and rationale: [`docs/crosswalks/acta-decision-receipts.md`](../../../docs/crosswalks/acta-decision-receipts.md).

All five fixtures are **real**: generated by an actual Ed25519 signer over
JCS-canonical bytes ([`gen.mjs`](gen.mjs) in this directory), not hand-typed
JSON. Each "invalid" case was produced by actually breaking a valid receipt
and re-verifying it, not asserted.

## Fixture cases

| File | Verification result | Interpretation |
|---|---|---|
| `01-valid-accepted.json` | valid | A safe tool call the policy permitted. |
| `02-valid-denied.json` | valid | A destructive tool call the policy blocked, evidenced with the same rigor as an allow. This is the property most receipt formats miss: a denial is not an absence of evidence, it is its own signed record. |
| `03-signature-key-mismatch.json` | invalid | `01-valid-accepted.json`'s envelope, verified against an unrelated real keypair. Fails as expected; included to show a wrong-key check, not to imply the file itself is malformed. |
| `04-broken-chain.json` | invalid | `02`'s envelope with `payload.parent_receipt_hash` overwritten after signing. The signature no longer matches the canonical bytes, so this fails signature verification, not a separate chain check; a broken chain and a broken signature collapse to the same failure because the chain pointer is inside the signed payload. |
| `05-stale-policy-digest.json` | valid signature, stale binding | `01`'s envelope, unmodified. The Ed25519 signature verifies cleanly: the receipt was not tampered with. But `payload.policy_digest` no longer matches the policy bundle in force at verification time (the policy was rotated after this receipt was issued). This is the case the thread's `policy_digest` / verifier-drift discussion (trace-spec#97, A2A composable-trust-evidence-format discussion) is about: cryptographic validity and policy freshness are different checks, and a verifier that only checks the signature will pass a receipt whose authorization basis has since changed. |

## Verifying independently

Each fixture is a standalone `draft-farley-acta-signed-receipts-02` envelope.
To check any of them without this repo's tooling:

1. Remove `signature` from the JSON.
2. Serialize the remaining `payload` object as compact JCS (RFC 8785: recursively sort object keys, no whitespace).
3. Verify `signature` as an Ed25519 signature over those bytes, against the public key in `signer-public-key.txt`.

`03` and `04` are expected to fail step 3. `05` is expected to *pass* step 3
(the signature is genuinely valid); the staleness is a separate check against
`payload.policy_digest`, which a TRACE profile would define by matching it to
the currently-bound policy bundle digest, not by cryptographic verification.

## Boundary

Same boundary the embodied profile states, generalized: a valid Acta receipt
proves a specific policy decision, over a specific tool call, was signed by
the operator's gate at a specific time, and that the record has not been
altered since. It does not prove the tool call's real-world side effect was
safe, correct, or reversible, and (per `05`) signature validity alone does not
prove the policy binding is still current.
